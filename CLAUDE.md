## Project summary

PathKit is a TypeScript CLI tool that statically analyzes a Temporal workflow file, finds every possible execution branch (if/else, try/catch around activities, `Promise.race` timeouts, `condition()` signal-waits, retry loops), builds a graph of every possible path through the workflow, and renders it as a Mermaid diagram. v1 covers this analysis only ("Gap 1" in `temporal-pathkit-idea.md`) and is complete as of M7. Gap 2 — coverage tracking of which paths tests actually exercise, via a new `pathkit coverage` subcommand — is under active development as of milestone G0; see the "Gap 2" section of `PLAN.md` for its milestone checklist.

## Locked architecture decisions

- **AST tooling:** `ts-morph`, not the raw TypeScript compiler API — chosen for a friendlier surface given the project author has limited coding experience.
- **Test framework:** Jest (with `ts-jest`), matching Temporal SDK's own testing conventions.
- **Package manager:** npm.
- **Scope:** single-file analysis only — no cross-file import resolution, no cross-project type resolution. See `LIMITATIONS.md`.
- **Activity-call detection:** a same-file syntactic heuristic (trace a call back to a local `proxyActivities()`/`proxyLocalActivities()` result), not TypeScript type-checker resolution. See `LIMITATIONS.md`.
- **Function scope:** only **exported** top-level functions in a file are treated as workflow entry points; non-exported helpers are ignored.
- **`switch` statements:** deliberately deferred out of v1 branch detection (M2); not detected as branch points.
- **Determinism:** node/edge/path ordering must be identical across runs on the same input (source-order AST traversal).
- **Cycles:** retry loops produce a labeled back-edge in the graph, not infinite unrolling; path enumeration treats a loop as "taken once" vs. "not taken" and enforces a hard `maxPaths` cap (default 2000, confirmed with the user before M6).
- **Temporal SDK version pinned for development:** `@temporalio/workflow` and `@temporalio/testing` `^1.24.0`. (Note: there is no `@temporalio/sdk` package — an earlier plan draft referenced it incorrectly.)
- **TypeScript version pinned:** `^6.0.3`, not the newer `7.x` line, because `ts-jest@29` and `@typescript-eslint@8` do not yet support TypeScript 7.

## 2026-09-16 — Syntax-validity check uses `Program.getSyntacticDiagnostics`, not `LanguageService`

M1 needed a way to detect "syntactically invalid TypeScript" and throw a clear error. `ts-morph`'s `LanguageService` has no `getSyntacticDiagnostics` method (that was an incorrect assumption in an early draft of `src/parser.ts`); `SourceFile.getPreEmitDiagnostics()` exists but returns *semantic* diagnostics too (type errors, unresolved imports), which would wrongly flag a syntactically valid file that imports `@temporalio/workflow` (needed from M3 onward) as broken, since that import can't resolve when a workflow file is parsed in isolation. The correct call is `project.getProgram().getSyntacticDiagnostics(sourceFile)`, which is syntax-only and won't false-positive on unresolved imports or type errors. `src/parser.ts` uses this exclusively for the "invalid syntax" check.

## 2026-09-16 — `demo/` manual check uses a throwaway script for M3–M6, not `pathkit analyze`

The plan's "manual step" for re-checking `demo/` files says to run `pathkit analyze` and paste the result into the Mermaid Live Editor — but that CLI command and Mermaid rendering don't exist until M7. For M3 through M6, the manual check instead uses a small scratch script (not part of the shipped package, not committed) that calls whatever library functions exist so far (`parseWorkflowFile`, `detectBranches`, etc.) directly against each `demo/` file and prints the raw result for visual inspection. Once M7 wires up the real `pathkit analyze` command and Mermaid output, the manual check switches to the originally planned Mermaid Live Editor workflow.

## 2026-09-16 — Activity-call recognition covers three same-file shapes, found by checking real code

Before writing M3's detector, real usage was checked directly: the SDK's own `proxyActivities` doc comments (in `node_modules/@temporalio/workflow/lib/workflow.d.ts`) show only the destructured form (`const { foo } = proxyActivities(...)`), but a search across all ~80 `workflows.ts` files in `temporalio/samples-typescript` found real production-style code using the whole-proxy-object form too (`const acts = proxyActivities(...); acts.foo()`, e.g. `worker-specific-task-queues/src/workflows.ts`, where the binding happens *inside* a function body, not just at top level). The SDK docs also show a third real shape: `foo.executeWithOptions(options, args)`, a per-call options override on a destructured activity function. `src/activityProxies.ts` recognizes all three. It does not recognize a proxy result re-destructured from an intermediate variable in a separate statement, or one passed into another function — see `LIMITATIONS.md`.

## 2026-09-16 — `condition()` has a built-in timeout form; `Promise.race` timers aren't restricted to activity calls

Checked before writing M4: `@temporalio/workflow`'s own `condition()` has three overloads — `condition(fn)` (wait only), `condition(fn, timeout)`, and `condition(fn, timeout, options)` — so a single detector marks a `condition()` call as a signal-wait branch and sets `hasTimeout` from the argument count, rather than treating the timeout form as a separate branch kind. Separately, real code search (`sleep-for-days/src/workflows.ts`: `Promise.race([sleep('30 days'), condition(() => isComplete)])`; `timer-examples/src/workflows.ts`: `Promise.race([processOrderPromise, sleep(ms)])`) showed the non-timer side of a `Promise.race` is not always an activity call — it can be a `condition()` call or an arbitrary promise variable. `src/timersAndSignals.ts` therefore only requires *one* race element to resolve to a `sleep()` call; it does not require or check the shape of the other elements. Refactored the shared "does this subtree contain a call matching X" traversal (used by both this and M3's try/catch detector) into `src/astUtils.ts`, and the shared "find the local name(s) a set of exports from a module are bound to" logic into `src/temporalImports.ts`, replacing `activityProxies.ts`'s original module-specific copy of that logic.

## 2026-09-16 — Graph construction is a single top-to-bottom statement walk, not built from the M2–M4 flat branch lists

The plan's M5 wording ("turn the ordered, possibly-nested branch list from M2–M4 into a directed graph") could be read as reassembling a graph from those detectors' flat output lists, but those lists (from `detectBranches`, `detectActivityTryCatchBranches`, `detectTimerAndSignalBranches`) don't carry parent/child nesting or sequencing information — only a location and a description. `src/graph.ts` instead walks each function's actual statement tree directly (via a `processStatements`/`processStatement` recursion threading an "open edges" frontier through sequential statements), calling the same underlying predicates (`isActivityCall`, `classifyTimerOrSignalCall`, etc.) at each relevant construct. This is the only way to get correct nesting (a branch's decision node hangs off its parent's specific edge) and correct loop back-edges. The M2–M4 detector functions are unchanged and still independently tested and used as-is; `graph.ts` is a new, independent consumer of the same lower-level predicates, not a caller of those four detector functions.

A retry loop's decision node gets exactly one labeled `"retry"` back-edge per path that falls through its body without an early `return`/`throw` — verified concretely on `demo/report-polling-workflow.ts`, whose two internal `if` checks (`status === 'complete'`, `status === 'failed'`) each independently reach either `End` (early return) or the loop's back-edge (falls through to retry), producing exactly the cycle the plan requires. Building the graph is a single linear pass over the statement tree regardless of any loop present — it never "runs" the loop — so there is no risk of this step itself hanging; that concern is deferred to M6's path enumeration, which is the milestone that actually walks the graph's paths.

## 2026-09-16 — Path enumeration terminates on cycles via "never reuse an edge within one path," not explicit back-edge detection

M6 needed depth-first path enumeration over M5's graphs to terminate even when a graph is cyclic. Rather than specifically detecting which edges are "back-edges" (e.g. by label, or by checking whether the target node is already on the recursion stack) and special-casing them, `src/paths.ts` uses a simpler, more general rule: a single path may never traverse the same edge (by array index, not just by label) twice. Since a graph has finitely many edges, this bounds every path's length and guarantees termination for any graph, with no separate cycle-detection logic needed. For an acyclic graph the constraint never actually triggers (a plain depth-first walk never revisits an edge anyway), so it has no effect on M2–M4's path counts. For the M5 retry-loop fixture this produces exactly the plan's desired behavior: the loop's `"retry"` back-edge can be taken once (producing one path that shows a retry happened) but a second attempt to take the same edge is blocked, forcing that path to exit the loop instead of recursing forever — verified against `demo/report-polling-workflow.ts` too (4 real paths found, `enumeratePaths` itself under 1ms).

`maxPaths` defaults to 2000 (confirmed with the user before starting M6) and applies uniformly to cyclic and acyclic graphs alike — a `pathological-explosion` fixture (12 independent, non-early-returning if/else pairs, 2^12 = 4096 possible paths) confirmed truncation kicks in correctly on a purely acyclic graph too, not just a cyclic one.

## 2026-09-16 — Mermaid output verified against the real `mermaid` parser, not just eyeballed

M7's Mermaid rendering (`src/mermaid.ts`) uses a stadium shape (`id(["text"])`) for Start/End and a rhombus (`id{"text"}`) for decision nodes, with HTML-entity escaping (`&`, `<`, `>`, `"`, `'`) on all label text — needed because real generated labels contain parentheses, quotes, and comparison operators (e.g. `if (status === 'complete')`, `for (let attempt = 1; attempt <= maxAttempts; attempt++)`). Before committing to this format, it was checked against the actual `mermaid` npm package's own `parse()` function (via a throwaway script using `jsdom` for the DOM APIs `mermaid` expects — not installed as a project dependency), which confirmed all of the rendered fixture and demo outputs, including the retry-loop cycle and the most special-character-heavy labels, parse as valid Mermaid syntax. `@mermaid-js/parser` (a newer, DOM-free parser package) was tried first but doesn't support the `flowchart` diagram type, hence the fallback to the full `mermaid` package for this one-time validation.

## 2026-09-16 — CLI is a thin `bin/pathkit` launcher over a testable `src/cli.ts`, with `pretest` rebuilding `dist/`

`bin/pathkit` only requires `../dist/cli` and calls its exported `runCli(argv, io)`, passing `process.stdout`/`process.stderr` writers and using the returned number as the exit code — all real logic (argument parsing, error handling, orchestrating parse → build graph → enumerate paths → render Mermaid, `--out` file writing) lives in `src/cli.ts` so it's type-checked and unit-testable. Because the CLI-level tests (per the plan) spawn the actual built `bin/pathkit` as a subprocess, `dist/` must exist before `npm test` runs; a `pretest` script (`npm run build`) was added so this is automatic both locally and in CI, rather than relying on a human or CI step to remember to build first. A `prepublishOnly` script was added for the same reason at publish time. Only `PathKitError`s (missing file, invalid syntax) are caught and turned into a clean stderr message + exit code 1; an unexpected error is deliberately allowed to crash with its real stack trace rather than being swallowed, consistent with the project's "fail clearly, don't hide problems" philosophy — the CLI-level tests only cover the specific, expected error cases the plan lists.

## 2026-09-16 — `ts-morph` was a devDependency despite being required at runtime; added a real-install smoke test

Post-v1, a report that `dist/bin/pathkit` didn't exist and might break `npm publish` turned out to rest on an incorrect assumption (`bin/pathkit` was never meant to be compiled into `dist/` — it's a hand-written JS launcher checked into `bin/` directly, and `package.json`'s `bin` field correctly points at `./bin/pathkit`, verified with an actual `npm pack` + tarball extraction + run). But investigating it surfaced a real bug in the same area: `ts-morph` was listed under `devDependencies`, even though every `dist/*.js` file that does real work (`graph.js`, `parser.js`, etc.) requires it at runtime. Since npm never installs a dependency's own `devDependencies` for a downstream consumer, `npm install @nikhilrajutirlange/pathkit` would install fine but immediately crash on first use with `Cannot find module 'ts-morph'` — a bug invisible from the source checkout, where devDependencies are already present in `node_modules`. Moved `ts-morph` to `dependencies` (it's the only package `src/` actually imports — `@temporalio/workflow`/`@temporalio/testing` are correctly devDependencies, only ever appearing as string module-specifier checks or referenced for research, never imported).

To catch this class of bug automatically rather than by manual inspection, added `scripts/smoke-test.js` (`npm run smoke`, wired into CI after the test step and into `prepublishOnly`): it builds, runs a real `npm pack`, installs the resulting tarball into a throwaway separate "consumer" project (the only way to accurately simulate what a real downstream `npm install` actually pulls in), and runs the installed `pathkit --version` and `pathkit analyze` against a sample workflow file. Verified this script actually catches the bug (not just passes trivially) by temporarily reverting the `dependencies` fix and confirming the smoke test fails with a clear message; restored the fix afterward.

## 2026-09-16 — Gap 2 (G0): `@temporalio/client`/`@temporalio/worker` added as `devDependencies`, not `dependencies`

Gap 2 (workflow path coverage tracking) needs real code somewhere that spins up a Temporal `Worker` and `Client` against `TestWorkflowEnvironment` to run an instrumented workflow copy and query its recorded trace. That code is never PathKit's own shipped `dist/` — PathKit's shipped surface only ever (a) writes an instrumented copy of a workflow file as text (`src/instrument.ts`, from G2 onward) and (b) reads/merges JSON trace files someone else produced (`src/coverageReport.ts`, from G8). The actual `Worker.create()`/`TestWorkflowEnvironment`/`Client` orchestration happens inside the **end user's own jest test file**, calling two small, Temporal-import-free helper functions PathKit exports (`prepareCoverageRun`, `recordCoverageTrace`, shipped in G10) — and that user's project already depends on `@temporalio/worker`/`@temporalio/client` itself, since it's testing a live Temporal workflow. So `@temporalio/client` and `@temporalio/worker` (`^1.24.0`, matching the existing SDK pin) are added to PathKit's own `devDependencies` only, exactly like `@temporalio/workflow`/`@temporalio/testing` already are — needed to write and run PathKit's *own* end-to-end tests (from G4 onward) proving the mechanism works, never needed by a downstream consumer's `npm install @nikhilrajutirlange/pathkit`. This is the same class of question the "`ts-morph` was wrongly a devDependency" bug (above) turned on, considered explicitly this time rather than discovered after the fact; G10's extended smoke test installs the packed tarball *and* the four `@temporalio/*` packages into a throwaway consumer project and runs a real jest test using only the two helpers, to prove this placement concretely rather than just by reasoning.

Also decided at G0: how a graph decision node maps back to a precise AST insertion point for instrumentation. Rejected a `{line, column}` field on `WorkflowGraphNode` (fragile — inserting text into the instrumented copy shifts every later line number, making "the same" node hard to re-find by position after a mutation) and a fully independent `instrument.ts` AST walk mirroring `graph.ts`'s construct-detection logic from scratch (risks silently drifting out of sync as `graph.ts` evolves). Instead, `GraphBuilder` (which already holds the live `ts-morph` `Node` at every `createNode(...)` call, today discarded) will gain a new, additive, non-breaking function `buildWorkflowGraphWithNodeRefs` (G1) returning the existing `WorkflowGraph` plus a `Map<string, Node>` from decision-node id to its exact AST node. Hard invariant, to be documented in `LIMITATIONS.md` at G1: a `Node` reference is only valid against the exact `ts-morph` source it came from, so instrumentation must always call this fresh against the **instrumented copy's own** parse, before any text is inserted into it — never against refs captured from analyzing the original file.

Naming conventions fixed at G0 for everything downstream: the instrumented sibling file is named `<sourceName>.<functionName>.<uniqueId>.pathkit-instrumented.ts` (function name included since coverage is per-function and a file can export several workflow functions; `uniqueId` is the full, untruncated output of `crypto.randomUUID()` — truncating it would throw away the entropy the concurrency-safety guarantee, added from G2 onward, actually depends on) and lives as a sibling of the original file (not a temp directory elsewhere), since Webpack's `workflowsPath` bundling resolves the workflow file's own relative imports from its own on-disk location. Trace files live at `.pathkit/coverage/<functionName>-<uniqueId>.json` in the consuming project, gitignored, with no config file in this pass. Both `*.pathkit-instrumented.ts` and `.pathkit/` were added to `.gitignore` at G0, ahead of any code that generates them.

## 2026-09-16 — Gap 2 (G1): `buildWorkflowGraphWithNodeRefs` implemented as planned at G0

Implemented the additive node-ref side-channel decided at G0: `src/graph.ts`'s `GraphBuilder` already held the live `ts-morph` `Node` at every `createNode(...)` call site and was discarding it — it now optionally records it in a private `nodeAstRefs: Map<string, Node>` (accepted as an optional third `astNode` parameter to `createNode`), threaded through from `processIf`/`processTry`/`processLoop` (which pass the `IfStatement`/`TryStatement`/`WhileStatement`/`ForStatement` itself) and from `processStatement`'s `Promise.race`/`condition()` handling (which passes the matched `CallExpression` — the precise node G6 will need to rewrite later, not just the enclosing statement, so `classifyStatement` was changed to return the matched call node alongside its classification instead of discarding it). A new exported `buildWorkflowGraphWithNodeRefs(fn, functionName)` returns `{ graph, nodeAstRefs }`; the existing `buildWorkflowGraph` is now a one-line wrapper around it that only returns `.graph`, so its return value, signature, and all Gap 1 callers (`mermaid.ts`, `paths.ts`, `cli.ts`, all M2–M6 tests) are completely unaffected — verified by `test/graph.test.ts` passing unmodified. New coverage in `test/graphNodeRefs.test.ts` confirms: a flat if/else's decision node maps to a real `IfStatement` whose condition text matches the source; a nested if/else's two decision nodes map to two distinct `IfStatement` nodes (not the same one twice); `start`/`end` nodes have no map entry; and `buildWorkflowGraph`'s output is structurally identical to `buildWorkflowGraphWithNodeRefs(...).graph` for the same input. The "never reuse a `Node` ref across a different parse" invariant from G0 is recorded in `LIMITATIONS.md`'s Gap 2 section. No new dependency this milestone.

## 2026-09-17 — Gap 2 (G2): instrumented sibling copy, unmodified text apart from a generated-file banner

`src/instrument.ts`'s `writeInstrumentedCopy(workflowFilePath, functionName)` implements exactly the G0-decided naming/placement conventions and nothing more yet: it reads the original file's text with `readFileSync`, prepends a two-line `// AUTO-GENERATED by pathkit coverage` banner (naming the source file and function, so a developer who stumbles on one of these files in their working directory understands what it is and that it's safe to delete), and writes it to a sibling `<sourceName>.<functionName>.<uuid>.pathkit-instrumented.ts` — same directory as the original (the relative-import landmine from research), with `uuid` from a fresh, full `crypto.randomUUID()` per call so repeated calls (parallel test workers, repeated runs) never collide, verified directly by a test that calls it twice in a row and asserts two distinct, both-existing files. `removeInstrumentedCopy` is `fs.rmSync(path, { force: true })` — safe to call on an already-deleted path, since cleanup code (this milestone's own tests' `afterEach`, and later `prepareCoverageRun`'s `cleanup()`) must never itself throw. A missing source file throws `PathKitError` (`"Workflow file not found: ..."`), mirroring `parser.ts`'s existing pattern, rather than failing with an opaque `ENOENT` from `fs`. No real instrumentation (tracking calls, query, imports) is inserted yet — that starts at G3; this milestone only proves the file-placement/naming/concurrency mechanics work, checkable by a plain `diff` between the original and generated file (only the banner differs). No new dependency this milestone.

## 2026-09-17 — Gap 2 (G3): real if/else instrumentation, all edits computed against the pristine parse and applied as plain text splicing

`writeInstrumentedCopy` now inserts real tracking into if/else decision points, using `buildWorkflowGraphWithNodeRefs` (G1) to find each `IfStatement` and the exact position of its `true`/`false` edge within `graph.edges` (the baked-in "edge index" a push call records). Every insertion point and replacement span is computed as a plain numeric `{start, end}` offset against the original, unmutated file text, collected into a flat list, and applied in one pass by sorting all edits by descending `start` and splicing strings — never via repeated `ts-morph` node-mutation calls. This directly follows from G1's "a `Node` ref is only valid against the exact parse it came from" invariant: a first mutation via `ts-morph`'s own API would invalidate every other node reference gathered from the same parse, forcing an awkward re-parse-and-re-match between every single edit. Plain offset arithmetic sidesteps that entirely — since edits are applied highest-offset-first, inserting or replacing text at one position never shifts the still-to-be-applied positions of any edit below it.

A `then`/`else` arm that's already a `Block` gets its push call inserted right after the opening `{`. An arm that isn't a `Block` — a single bare statement (`if (x) return 'a';`) or a nested `if` (an `else if (...)` chain, since TypeScript's AST represents `getElseStatement()` as the inner `IfStatement` node directly, not wrapped in a block) — is wrapped in a synthesized `{ push(...); <original arm> }`, which is syntactically valid and behaviorally identical to the original in both cases; handling both non-block shapes with the same wrap logic avoids a separate, more fragile "else-if chain" special case. A missing `else` altogether gets a brand-new `else { push(...); }` appended after the `then` arm's end. All three shapes were checked concretely — with real generated output eyeballed via `diff`/`cat`, plus a re-parse via `ts-morph`'s syntactic diagnostics confirming zero syntax errors — against fixtures covering a flat if/else, a no-else if, a fully braceless if/else, and Gap 1's own nested if/else fixture (`test/fixtures/m2/nested-if-else.ts`, reused directly per the plan review's explicit ask, confirming the two nested decision nodes get distinct, correctly-indexed push calls rather than only ever being proven on a single flat case).

The coverage query itself is namespaced per function as `__pathkit_coverage__<functionName>` (both the `defineQuery` call's registration-name string and its local variable name — safe because `functionName` is already guaranteed to be a valid JS identifier by `parser.ts`'s exported-function detection), so a file with multiple exported workflow functions can be instrumented one at a time without any query-name collision. Its handler, registered via `setHandler(...)` as the literal first statement of the function body (so it's live before anything else in the workflow can run), is `() => [...__pathkitTrace__<functionName>]` — synchronous (required: Temporal query handlers must not be `async`) and read-only (required: they must not mutate workflow state; returning a fresh copy of the trace array, rather than the array reference itself, is a defensive habit here, not a correctness requirement, since the array is a plain in-memory value read after the fact). The trace array itself is populated purely by ordinary, synchronous `Array.prototype.push` calls inserted directly at each branch arm — this is safe under Temporal's replay mechanic specifically because workflow control flow is already required to be deterministic (same inputs and history replay to the same branches every time), so a replay re-executes the exact same sequence of pushes in the exact same order on every replay; the trace is not an independent side effect that could desync from history, it is a deterministic function of the same deterministic control flow the SDK already requires, and the query is only ever read after the workflow's real execution completes (never queried mid-replay by this design), so there is no risk of ever observing a partially-replayed trace.

Module-level scaffolding (the trace array's `const` declaration and the query definition) is inserted directly after the last existing `import` declaration (or at the very top of the file if there are none). The `defineQuery`/`setHandler` import is merged into an existing `@temporalio/workflow` named-import statement when one exists (checked and confirmed against a fixture that already imports `proxyActivities` from that module), or a new import statement is added when none exists. Two import shapes are deliberately not supported yet and fail loudly with a `PathKitError` rather than silently mis-instrumenting: a namespace import (`import * as workflow from '@temporalio/workflow'`) and a bare side-effect-only import — both are rare in real Temporal workflow code (the SDK's own docs and every real sample use named imports), so this is a narrow, documented gap (`LIMITATIONS.md`) rather than a design flaw. A function with an implicit-return arrow body (`async () => expr`, no `{ }` block) has nowhere to insert the `setHandler` call and also fails loudly with a clear `PathKitError`, rather than silently shipping an uninstrumented copy that still claims to support coverage. No new dependency this milestone.

## 2026-09-17 — Gap 2 (G4): first real end-to-end proof, and a real bug found in the process — a Query issued after `worker.runUntil()` resolves hangs forever

`test/coverage-e2e.test.ts` is PathKit's own dev-only test suite (never shipped) proving G3's if/else instrumentation actually works against a real `TestWorkflowEnvironment.createTimeSkipping()` + a real `Worker` bundling and running the instrumented copy, for a trivial if/else fixture (both branches) and a zero-branch fixture (confirming an empty trace and no crash when there are no decision nodes at all). Confirmed concretely by first debugging this outside Jest with a plain Node script (`worker.runUntil(handle.result())` then, separately, `handle.query(...)` after `runUntil` resolved) — the query **hung indefinitely**, reproduced identically inside Jest too, so this was a real mechanism bug, not a test-harness quirk. The cause: `runUntil` stops the Worker's poll loop once its promise resolves, but a Query is answered by a Worker replaying/holding the workflow's sandboxed state, not read directly from server-stored history — once no Worker is left polling that task queue, a Query dispatched to it has nothing to answer it and never resolves. The fix, now baked into `test/coverage-e2e.test.ts`'s `runAndQueryTrace` helper: issue the query **inside** the same `worker.runUntil(async () => { await handle.result(); return handle.query(...); })` callback, so the Worker is still polling when the query is dispatched. This is the actual real-world shape any downstream user's own test (and G10's `prepareCoverageRun`/`recordCoverageTrace` helper docs) must follow too — querying after a Worker has already stopped is a landmine worth calling out explicitly in G10's README example, not just here.

Also completed at G4: the CI workflow (`.github/workflows/ci.yml`) now caches `TestWorkflowEnvironment`'s downloaded ephemeral test-server binary (confirmed by direct observation to land at `/tmp/temporal-test-server-sdk-typescript-<version>`, ~80MB, not a persistent OS cache directory) via `actions/cache`, keyed on `package-lock.json`'s hash, so the network download only happens on a cache miss (a version bump) rather than every CI run. `npm run smoke` was re-run and confirmed the consumer-project install still only pulls in `ts-morph` (11 packages total) — `@temporalio/worker`/`@temporalio/client` did not leak into the published tarball's runtime dependency graph, direct proof of the G0 dependency-placement decision now that live Temporal code actually exists in the dev test suite. A manual walkthrough against a real `demo/` fixture (`demo/order-processing-workflow.ts`, driving its `amountCents <= 0` rejection path to avoid needing activity mocks it doesn't have yet) confirmed the mechanism end-to-end on real (not toy) workflow code: the if-decision's true edge was correctly recorded, and the file's other decision node (a try/catch around an activity call, not yet instrumented until G5) was correctly left untouched.

## 2026-09-17 — Gap 2 (G5): try/catch-around-activity instrumentation, plus two more real bugs found by actually running it

`tryCatchEdits` in `src/instrument.ts` inserts a `push()` for the "success" edge as the literal last statement of the `try` block (right before its closing `}`) and a `push()` for the "failure" edge as the first statement of the `catch` block — mirroring G3's approach of computing exact offsets against the pristine parse and applying them alongside the if/else edits in one splice pass. Verified at the text/AST level against Gap 1's own `test/fixtures/m3/try-catch-around-activity.ts` (reused directly, matching G3's established pattern of reusing Gap 1 fixtures rather than only ever inventing new ones) and confirmed it correctly leaves `test/fixtures/m3/try-catch-non-activity.ts` untouched (that try/catch wraps `JSON.parse`, not a recognized activity call, so Gap 1 never creates a decision node for it), and composes correctly with if/else instrumentation in the same function using the real `demo/order-processing-workflow.ts` shape (2 if/else pushes + 2 try/catch pushes, all four present and correctly indexed).

Building the first real e2e test for this (`test/coverage-e2e.test.ts`'s new "G5" describe block, sharing G4's single `TestWorkflowEnvironment` per the SDK's own reuse recommendation) surfaced two more real, non-obvious bugs, neither of them in PathKit's own code:

1. **A try body's own early return can make the success push dead code.** The first attempt at a G5 e2e fixture had `try { return await doWork(); } catch (err) { return 'failed'; }` — a `return` as the try block's ONLY statement. Since the success push is inserted textually after the try block's last statement, and that statement was itself a `return`, the push became unreachable dead code (confirmed directly: `cat`-ing the generated file showed the push sitting after the `return`, and the resulting trace on a successful run was empty instead of `['<successIdx>']`). Fixed by changing the fixture to the realistic, common shape instead (`try { await doWork(); } catch { return 'failed'; } return 'succeeded';`, matching `demo/order-processing-workflow.ts`'s and Gap 1's own M3 fixture's shape) rather than trying to special-case early-return try bodies in the instrumenter itself. This is now a documented `LIMITATIONS.md` bullet — the push can be *skipped* for a rare shape, but is never *wrong* (it can't fire on an execution that actually threw, since it's textually after everything that could throw).
2. **Temporal's default activity retry policy retries forever, hanging the "failure" test case.** The first attempt at the failure-path e2e test mocked `doWork` to always reject and expected the `catch` block to run — instead the whole test hung until Jest's timeout. Cause: `proxyActivities` defaults to an unbounded retry policy, so a mock that always rejects is retried indefinitely by the Worker rather than ever surfacing as a caught exception inside the workflow. Fixed by adding `retry: { maximumAttempts: 1 }` to the fixture's `proxyActivities(...)` options, so the first failure surfaces immediately. This is a fact about Temporal's own activity semantics, not a PathKit bug, but is exactly the kind of "real SDK shape, not an invented pattern" thing worth recording here so a future e2e fixture with a to-be-failed activity doesn't rediscover it the hard way.

No new dependency this milestone (G5).

## 2026-09-17 — Gap 2 (G6): `Promise.race`/`condition()` instrumentation, scoped to what `graph.ts` can actually produce (narrower than the plan's original wording)

Before writing any instrumentation code, re-checked `graph.ts`'s exact statement-dispatch order (`processStatement`) rather than assuming the plan's original wording ("handle a `condition()` used directly as an if/while condition") was achievable as written. It isn't: `processStatement` checks `if`/`try`/`while`/`for` and routes to their own handlers *before* ever calling `classifyStatement` (the function that recognizes `Promise.race`/`condition()` calls) — so a call embedded in one of those constructs' own test expression is absorbed into an ordinary `if` decision (already handled by G3) or a transparent loop, and never becomes a `Promise.race`/`condition()`-kind decision node at all. This was verified directly by reading `graph.ts` (not inferred) before implementation started, avoiding building unreachable-in-practice logic for a case that can't arise. The real, achievable scope — "plain" statements not already claimed by `if`/`try`/`while`/`for`/`return`/`throw` — is documented in `LIMITATIONS.md`, distinguishing it clearly from the plan's original phrasing.

Within that real scope, implemented: `Promise.race([...])` must be a bare, value-discarding statement (matches every real usage found in `temporalio/samples-typescript` during M4's original research); `condition(fn)` (no timeout) can appear in any such plain statement, since it has exactly one possible outcome, needing no value inspection at all; `condition(fn, timeout)` (with timeout) must be captured into its own variable declaration, since only the captured boolean tells its two outcomes apart. All three are enforced by inspecting the exact enclosing statement shape (via `astNode.getFirstAncestor(Node.isStatement)`) before rewriting anything — any other shape throws a `PathKitError` naming the exact restriction, verified concretely against two dedicated fixtures (`test/fixtures/g6/race-result-assigned.ts`, `condition-timeout-discarded.ts`) that each throw the expected error.

The generated `__pathkitRace(promises, labels)` helper (injected into the instrumented file only when the function actually contains a `Promise.race` decision node, to avoid unconditional bloat) is deliberately simpler than the plan's original `{ __pathkitLabel, value }` wrapper design: since the only supported usage always discards the race's resolved value anyway, the helper just resolves directly to `labels[i]` for whichever promise settles first — no value-preservation machinery is built for a case nothing currently needs. `test/instrumentRaceHelper.test.ts` extracts the helper's exact generated source text and instantiates it via `new Function(...)` to unit-test it in complete isolation (fast, no live Temporal run needed), confirming directly that wrapping a promise in an additional `.then()` never changes which side of a real race wins, including a genuine timing-based case (`Promise.resolve()` vs. a 50ms `setTimeout`).

Building the e2e proof (`test/coverage-e2e.test.ts`'s new "G6" describe block) surfaced two more real, non-PathKit bugs, continuing the pattern from G4/G5 of always running the mechanism for real before calling a milestone done:

1. **`sleep('10 millis')` is not a valid Temporal duration string** — the SDK's duration parser (built on the `ms` npm package's format) doesn't recognize "millis" as a unit; the workflow task threw synchronously, and because an *uncaught exception during workflow execution* (as opposed to an activity failure) triggers the SDK's own unbounded workflow-task retry, the test hung exactly like G5's activity-retry bug, but one layer up the stack. Fixed by using the correct `'100ms'` format. Recorded here so a future fixture author doesn't burn time rediscovering that "millis" isn't valid syntax.
2. **A `condition(fn, timeout)` with a long real-world-scale timeout (`'1 hour'`) intermittently hung when it was not the first `TestWorkflowEnvironment`-driven test in the file to actually need time-skipping to fire** (it passed reliably in isolation, and passed when it was the *only* test exercising the timeout path, but hung when run after several other tests had already created and torn down their own `Worker`s against the same shared `testEnv`). The exact mechanism wasn't pinned down further (plausibly the test server's auto-time-skip lock not being released promptly enough across several back-to-back `Worker.create`/`runUntil` cycles) — rather than chase a timing-sensitive SDK internal further, the fixture's timeout was shortened to `'200ms'`, a duration short enough to resolve quickly in real wall-clock time whether or not auto-skipping engages at all, sidestepping the fragility entirely for *this* fixture only. **This is explicitly an unresolved workaround, not a root-cause fix** — nothing prevents the same hang from resurfacing in a later milestone's fixture (G7's retry-loop tests, which will likely want to test a "wait/backoff before retrying" shape, are a real risk). `test/coverage-e2e.test.ts`'s own file-level doc comment now carries the standing rule this implies: every timer duration used in a live e2e fixture in that file must stay short (a few hundred milliseconds), never a "realistic" one, and a genuinely long timeout that must be tested needs its own isolated `TestWorkflowEnvironment`, not the shared one.

No new dependency this milestone (G6).

## 2026-09-17 — Gap 2 (G7): retry-loop instrumentation, plus a structural fix to `graph.ts` — an `outcomeEdgeIndex` map, not just label lookups

Retry-loop instrumentation itself is the simple half of this milestone: `retryLoopEdits` pushes the "iterate" edge as the first statement of the loop body and the "exit" edge immediately after the whole loop statement, deliberately with no separate push for the "retry" back-edge — a second (or third, ...) pass through the loop body simply re-executes the same "iterate" push, so a multi-iteration run's raw trace naturally contains the repeated pattern without any extra code. This is exactly the "a retry happened" signal `paths.ts`'s `enumeratePaths` already collapses a back-edge into.

The harder, unplanned half: the very first attempt to instrument a *real* retry-loop fixture (`test/fixtures/m5/retry-loop.ts`, one of Gap 1's own confirmed-real fixtures) crashed immediately with "if-decision node n2 is missing a true/false edge" — not a bug in the new retry-loop code, but a latent structural issue in `graph.ts` that G3/G5/G6's if/try/race/condition instrumentation had been silently exposed to since G3, just never triggered because no milestone before G7 had tried instrumenting a decision nested inside a retry loop. Root cause, traced directly in `graph.ts`: `processLoop`'s retry-closing step (`this.addEdge(edge.from, nodeId, 'retry')`) hardcodes the label `'retry'` for *any* open edge that falls through to the end of a loop body — discarding whatever that edge's original label was. Concretely, in `retry-loop.ts`'s `for` loop, an `if (status === 'complete') { return 'done'; }` with no `else` has its "false" continuation flow straight through to the loop's end (nothing else in the body consumes it), so that edge is persisted in `graph.edges` with the label `'retry'`, not `'false'` — confirmed directly by printing the graph (`{from: 'n2', to: 'n1', label: 'retry'}`, no `'false'`-labeled edge from `n2` exists at all). This is *intentional and correct* in Gap 1's own graph model (a single combined "retry" edge is exactly what `mermaid.ts`/`paths.ts` want, and Gap 1's own M5 decision log already describes "falls through to retry" this way) — but it broke every prior milestone's assumption that "a decision node always has its outcomes findable by searching `graph.edges` for the expected label."

The fix: `OpenEdge` (an internal `graph.ts` type, never exposed publicly) gained an optional `outcomeKey` field — a stable `${nodeId}#${originalLabel}` tag (e.g. `n2#false`) set once, at the exact moment a decision node's own outcome edge is created (in `processIf`/`processTry`/`processLoop`/the race-and-condition branches of `processStatement`, via a new small `outcomeEdge(nodeId, label)` helper). Because `OpenEdge` objects are threaded through `processStatements`/`processStatement` by reference, not cloned, this tag survives unchanged through any number of intervening non-branching statements or nested decisions, all the way to whichever of the three places finally closes it into a real `WorkflowGraphEdge` (`connectAllTo`, `finalize`'s terminal-edge loop, or `processLoop`'s retry-closing loop) — each of which now also records `outcomeKey → edges.length` (the edge's final array index) into a new `outcomeEdgeIndex: Map<string, number>`, additively returned from `buildWorkflowGraphWithNodeRefs` (a third field alongside `graph`/`nodeAstRefs`, non-breaking to every existing G1–G6 caller and test). `WorkflowGraph`/`WorkflowGraphEdge`/`WorkflowGraphNode` themselves are completely untouched — `mermaid.ts`, `paths.ts`, `cli.ts`, and every M2–M6 Gap 1 test are unaffected, confirmed by the full existing suite passing unmodified after this change.

All four of `instrument.ts`'s edit-generation functions (`ifElseEdits`, `tryCatchEdits`, `raceAndConditionEdits`'s `raceEdit`/`conditionEdit`, and the new `retryLoopEdits`) were updated to resolve every outcome index via a new shared `resolveOutcomeIndex(outcomeEdgeIndex, nodeId, outcome)` helper, never via `graph.edges.find(...)` by label — fixing this bug everywhere it could occur, not just for retry loops. Verified concretely: both `test/fixtures/m5/retry-loop.ts` and the real `demo/report-polling-workflow.ts` (which has *two* sequential ifs whose false-continuations chain into the loop's end, exactly the shape that broke) now instrument correctly and re-parse with zero syntax errors; new regression tests in `test/graphNodeRefs.test.ts` assert directly that `outcomeEdgeIndex` resolves an if's "false" outcome to an edge whose *persisted* label is `'retry'`, pinning this exact scenario down so it can't silently regress. The G7 e2e proof (mocking an activity to fail twice then succeed) confirms the resulting raw trace end-to-end: `['iterateIdx', 'falseIdx', 'iterateIdx', 'falseIdx', 'iterateIdx', 'trueIdx']`.

No new dependency this milestone.

Before moving on, the `outcomeKey`/`outcomeEdgeIndex` fix was independently verified to be a pure lookup-mechanism change with zero effect on generated output for anything that worked before: a git worktree of the pre-G7 commit was built alongside the current tree, and both versions' `writeInstrumentedCopy` were run against every G3/G5/G6 fixture (13 successful-instrumentation cases plus 3 error cases) — all 16 produced byte-identical instrumented text or identical `PathKitError` messages between the old label-search code and the new tag-based code. The only case where the two versions diverge is the new one G7 added (a decision nested inside a retry loop), which the old code couldn't handle at all.

## 2026-09-17 — Gap 2 (G8): trace format + offline merge, including a genuinely hard design question worked through by hand — what does "retried, then succeeded" collapse to?

`src/paths.ts` gained an additive `enumeratePathsWithEdgeIndices`, sharing its DFS with the existing `enumeratePaths` via a new private `enumerateIndexedPaths` (both public functions derive their output from the same walk, so `enumeratePaths`'s exact behavior is provably unchanged — confirmed by the existing `paths.test.ts` suite passing unmodified). New `src/coverageReport.ts` defines the trace JSON schema (`CoverageTraceFile`: `schemaVersion`, `workflowFile`, `functionName`, `sourceHash`, `recordedAt`, `rawTrace`) and `mergeCoverageTraces(workflowFilePath, functionName, traceFilePaths, options)`, which reads each trace file, validates `schemaVersion` and `sourceHash` (a plain `sha256` hex digest of the workflow file's raw text — `allowStale` opts out of the staleness check), and matches each trace's (collapsed) raw trace against a declared path by **edge-index identity**, not label text — necessary since two different decision points can share a label like `"true"`.

Before matching can work at all, declared paths need filtering: every declared path from `enumeratePathsWithEdgeIndices` includes the single, never-instrumented `''` connector edge from Start (and, for any decision, only its *tracked outcome* edges are ever pushed at runtime) — so `mergeCoverageTraces` filters each declared path's edge-index sequence down to only the edges present in `outcomeEdgeIndex`'s values before comparing it to a raw trace, or a zero-branch function's single trivial path would never match its own (correctly empty) raw trace.

The genuinely hard part was designing what "collapsing" a multi-iteration raw trace should actually produce, worked through by hand rather than guessed at. A raw trace like `[iterate, retryIdx, iterate, retryIdx, iterate, trueIdx]` (retried twice, then succeeded — a real trace G7's own e2e test produces) cannot be reconciled with **any** declared path if the retry portion is preserved as-is, for a structural reason specific to Gap 1's own graph model: after taking a loop's back-edge once, the only edge still available out of the loop's node is `'exit'` (the `'iterate'` edge that would otherwise re-enter the loop body has already been used, and `enumeratePaths` never reuses an edge within one path) — meaning **Gap 1's graph has no declared path at all that represents "retried, then succeeded via anything other than the loop's own exit."** Set-based (order-insensitive) matching doesn't rescue this either — the *set* of edges in a "retried then succeeded" trace still doesn't match any declared path's edge set.

Given this, `collapseRepeatedEdges` implements a specific, deliberate resolution: walk the raw trace left to right, and whenever an edge index repeats, **rewind** — discard everything recorded since (and including) its first occurrence, then continue from the repeat — so only the *most recent* pass through any cycle survives in the collapsed trace. Traced by hand: `[iterate, retryIdx, iterate, retryIdx, iterate, trueIdx]` collapses to `[iterate, trueIdx]`, matching the "succeeded" declared path — deliberately **discarding the fact that a retry happened at all** for this case, since Gap 1's graph has no path that preserves it. A "retried once then gave up" trace `[iterate, retryIdx, exitIdx]` needs no rewinding at all and matches the "retry, exit" declared path directly, since neither edge repeats. This is a real, accepted limitation (`LIMITATIONS.md`), not an oversight: the algorithm never *invents* a match to a declared path that isn't a genuinely valid walk through the graph — it only ever discards *how many times* a cycle repeated, consistent with Gap 1's own M6 decision log stance that a single "retry" edge already represents "a retry happened," not any specific count. The algorithm needs no special knowledge of which edges are "loop" edges at all — it's a fully generic sequence-cycle collapse, correct here only because, in every construct Gap 1 currently models, the sole way the same push() call site fires twice in one execution is a loop iterating.

Verified with a dedicated `test/fixtures/g8/two-loops.ts` (two independent, sequential retry loops, no shared decision nodes) and a hand-written raw trace exercising each loop at a *different* iteration count (3 and 2) — confirming the collapse normalizes each back-edge independently: the combined trace correctly collapses to the one declared path (of four — two independent binary choices) that takes both loops' retry edges, not just the single-loop case G7 already proved. Also verified: `enumeratePathsWithEdgeIndices` preserves Gap 1's `truncated` flag from `pathological-explosion.ts` (4096 real paths, capped at the default 2000), and `CoverageReport.truncated`/`totalPaths` surface it explicitly (`totalPaths: 2000`, not the true 4096) rather than presenting a percentage that looks more complete than it is. Malformed JSON, an unsupported `schemaVersion`, and a trace matching no declared path are all reported in `unmatchedTraces` (never silently dropped); a trace recorded for a *different* function is silently skipped, since a trace directory is expected to hold traces for many functions at once.

No new dependency this milestone (G8).

## 2026-09-17 — Gap 2 (G9): `pathkit coverage` CLI command, and a real gap found in the existing CLI test harness

Wired a `coverage` subcommand into `src/cli.ts` mirroring `analyze`'s conventions exactly: its own manual arg parser (`parseCoverageArgs`), only `PathKitError` caught and turned into a clean stderr message (anything else crashes with a real stack trace), report built as one string and written to both stdout and (if `--out` is given) disk. `pathkit coverage <file> --traces <dir> [--function <name>] [--out <path>] [--json] [--allow-stale] [--clean]` reads every `*.json` in `--traces <dir>`, calls `mergeCoverageTraces`, and by default prints a human-readable text report (total/covered/percentage — including the truncated-total case from G8 — and named covered/untested path lists); `--json` swaps in the serialized `CoverageReport` instead. If `--function` is omitted, the file's exported functions are inspected directly: exactly one is used automatically, zero or more-than-one is a clear error asking the user to pick with `--function` (a workflow file commonly exports several functions, but a coverage report is inherently per-function). `--clean` deletes every trace file just read, after the report has already been built and printed — never before, so `--clean` can never cause a report to look emptier than what was actually read. Unmatched-trace warnings are printed to stderr unconditionally, including in `--json` mode, exactly per the confirmed default.

Verified directly at the terminal, not just via automated tests: a hand-written trace against `demo/order-processing-workflow.ts` produces `Covered: 1/3 (33.3%)` with correctly-named covered/untested paths, `--json` output pipes cleanly through `jq`, `--clean` empties the traces directory while leaving the directory itself intact, and a missing/nonexistent `--traces` directory fails with a clear message rather than a raw Node `ENOENT` stack trace.

Writing the `--json`-mode-prints-unmatched-warnings-to-stderr test surfaced a real gap in the existing CLI test harness (`test/cli.test.ts`'s `runCliSubprocess`, in place since M7): it was built on `execFileSync`, which only exposes a subprocess's stderr via the exception it throws on a *non-zero* exit — on a successful (`exit 0`) run, `execFileSync` discards stderr entirely, hardcoding it to `''` in the existing harness's success branch. Every M7-era CLI test happened to only need stderr on a failing run, so this never mattered until `pathkit coverage` needed to assert on a stderr warning from a *successful* command (unmatched traces are a non-fatal warning, not a failure). Fixed by switching `runCliSubprocess` to `spawnSync`, which captures stdout/stderr unconditionally regardless of exit code — a one-line change to the shared harness, not a per-test workaround, and it doesn't change behavior for any of the pre-existing `analyze`/`--version` tests (confirmed by the full existing `cli.test.ts` suite passing unmodified).

`package.json`'s version was bumped `0.2.0` → `0.3.0` per the project's existing package-hygiene rule ("bump whenever CLI-facing behavior changes"), since `pathkit coverage` is new CLI-facing behavior; `package-lock.json` was resynced via `npm install --package-lock-only`. `README.md` gained its first real `pathkit coverage` usage section (flags, defaults, a worked example against the same `demo/order-processing-workflow.ts` fixture used in the manual terminal walkthrough above) and an updated status line.

No new dependency this milestone.
