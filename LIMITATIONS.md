# Known Limitations

PathKit is a static analysis tool. Rather than silently guessing at code it can't reliably interpret, it aims to either detect a pattern correctly or clearly not detect it at all. This file is the honest, complete list of what PathKit does and doesn't cover. The "Gap 1" section below was consolidated at the end of the v1 build (M7); the "Gap 2" section was consolidated at the end of the coverage-tracking build (G11). Nothing here was written speculatively ahead of implementation — everything is something that was actually checked or actually happened while building the corresponding milestone.

## Gap 1 — static path/branch analysis (scope boundaries, by design, not bugs)

- **Single-file analysis only.** PathKit analyzes one workflow file at a time, passed directly on the CLI. It does not follow imports, does not resolve helper functions defined in other files, and does not do cross-project type resolution. A workflow that splits its logic across multiple files will only show the branches visible in the file actually analyzed.

- **`executeChild()` calls to a child workflow in another file are not followed — a design question, not yet a bug fix.** Found piloting PathKit against a real multi-workflow project (`orderFulfillmentWorkflow`, which orchestrates four other workflows as children via `executeChild`): PathKit correctly parses and analyzes the file that *calls* `executeChild` (it's just an ordinary function call, invisible to branch detection unless its result feeds an `if`/`try`/loop condition in the same file), but has no notion that `executeChild(childWorkflow, ...)` refers to another *workflow file* with its own graph of paths, so the calling workflow's diagram never shows "what can go wrong inside the child" — a rejected/approved fraud check, a failed inventory reservation, etc. — only whatever the parent file's own code does with the child's settled result. This is consistent with the "single-file analysis only" scope above (this is exactly what that scope boundary predicts), but is called out on its own here because it's the single biggest practical gap for a project that's actually composed of child workflows calling other child workflows, and it's a genuinely open design question — not a small fix — whether/how a future version should follow `executeChild` across files (e.g. inlining the child's graph at the call site, vs. a separate "expand this child" command, vs. leaving it out of scope permanently): each option has real tradeoffs (inlining risks graph/path-count explosion for a deeply-nested composition; a separate command adds a second mental model; leaving it out of scope forever means a "full picture" diagram genuinely isn't achievable). Not attempted in this pass — flagged for a project-owner decision instead of guessed at.

- **`Promise.all`/`Promise.allSettled` are not detected as branch points at all.** Found in the same pilot project (`orderCancellationWorkflow`, which runs a child-workflow refund and an inventory-release activity concurrently via `Promise.allSettled`): PathKit's "What PathKit detects" list (see README) only covers `if`/`else`, try/catch-around-an-activity, `Promise.race` timeouts, `condition()` waits, and retry loops — `Promise.all`/`Promise.allSettled` aren't in that list, so a workflow whose only real branching is "which combination of parallel branches succeeded/failed" (a real, common Temporal pattern, not a contrived one) is reported as a single straight-line path with **zero** decision nodes and **one** total path, even though the workflow's actual behavior clearly branches on each settled outcome. This isn't a crash or a miscategorization of something PathKit claims to detect — it's a real, size-able gap in what's detected at all, silently and correctly (per the "either detect cleanly or don't detect at all" philosophy — it doesn't produce a *wrong* graph, just an incomplete one with no visible warning that anything was skipped). Whether/how to model `Promise.all`/`allSettled` (e.g. as a decision node with one outcome per combination of branch results, which multiplies combinatorially with the number of concurrent branches) is a real design question flagged here rather than guessed at.

- **A `throw` inside a `try` block does not route to that `try`'s own `catch` handler in the graph — it terminates straight to `End`, same as a `throw` anywhere else.** Found in the same pilot project's saga/compensation workflow (`orderFulfillmentWorkflow`): its `try` block contains an `if (shipment.status === 'exception') { throw ...; }` partway through, which at runtime is caught by the *same* `try`'s `catch` block (which runs saga-compensation logic) before re-throwing — but the graph shows that `if`'s `"true"` edge going directly to `End`, completely bypassing the `catch` block's compensation logic that would actually run. This under-represents the workflow's real behavior for exactly the case (a saga's mid-`try` failure branch) that a compensation-pattern workflow most wants visualized correctly, and it is not currently documented anywhere in this file. Fixing it correctly requires `processStatement` to thread "what's the nearest enclosing `catch` target" down through nested statement processing (mirroring the `break`-into-loop fix above, but for `throw`-into-`catch`) — a real, non-trivial control-flow change, not a one-line fix, and one with its own design questions (e.g. should a `throw` of a type the `catch` can't structurally distinguish from others still show as reaching the `catch`'s branches, given PathKit doesn't do any type analysis?). Flagged here as a real bug in a correctness sense, but treated as a design decision for how to fix rather than guessed at in this pass.

- **Only exported top-level functions are treated as workflow entry points.** A non-exported helper function in the same file — even one containing branches, activity calls, or loops — is not analyzed as a workflow, since it can't be run directly by a Temporal worker. Both `export async function x() {}` and `export const x = async () => {}` styles are recognized.

- **Activity-call detection is a same-file syntactic heuristic, not type resolution.** A call is treated as "an activity call" when it can be traced, within the same file, back to a local `proxyActivities()` / `proxyLocalActivities()` result. Three real-world shapes are recognized: a destructured call (`const { foo } = proxyActivities(...); foo()`), a call through a bound proxy object (`const acts = proxyActivities(...); acts.foo()`, including when bound inside a function body, not just top-level), and the SDK's documented per-call override (`foo.executeWithOptions(options, args)` on a destructured activity). PathKit does not use the TypeScript type checker to resolve the activity interface across files, and does **not** recognize: a proxy result re-destructured from an intermediate variable in a separate statement (`const acts = proxyActivities(...); const { foo } = acts;`); a proxy result passed into another function or stored in a nested object/array property; or an activity call wrapped in a custom helper function rather than called directly.

- **`switch` statements are not detected as branch points.** Only `if`/`else` is walked for condition branches. A `switch` in a workflow function is simply invisible to the graph — it does not crash the tool and does not appear as a branch, decision node, or path split. This is a deliberate v1 scoping decision, not an oversight: `switch`-based branching can be added in a later version if there's demand.

- **`Promise.race` timeout detection requires a literal array at the call site.** `Promise.race([a, b])` is recognized; `Promise.race(promises)` (a variable holding the array) is not, since that would require tracing the array's contents rather than reading them off the call. Within a recognized race, the "timer" side must be a direct or nested call to `sleep(...)` imported from `@temporalio/workflow` in the same file — a custom wrapper function that calls `sleep()` internally elsewhere is not recognized, for the same same-file-heuristic reason activity wrapper functions aren't recognized. The race's non-timer side is not required to be any particular shape (real code shows it can be an activity call, a `condition()` call, or an arbitrary promise variable).

- **`condition()` is recognized by argument count, not type-checked.** Its 1-argument form (wait only) and 2-or-more-argument form (wait with timeout) are both recognized purely from how many arguments are passed, with no attempt to verify the timeout argument's type. Signal registration itself (`defineSignal`, `setHandler`) is not treated as a branch point — only the `condition()` call where execution actually waits is; the branching happens at the wait, not at the handler registration.

- **Only a `while`/`for` loop wrapping a recognized activity call becomes a cycle in the graph** (a labeled `"retry"` back-edge). A loop with no activity call inside it is walked through transparently, once, with no cycle modeled — consistent with try/catch only being a branch when it wraps an activity. A `continueAsNew()`-based recursive pattern (a workflow re-invoking itself instead of looping) is **not** recognized as a cycle at all in v1 — only literal `while`/`for` loops are.

- **An unlabeled `break` inside a loop correctly exits to whatever comes after the loop, merged with the loop's own `"exit"` outcome — a labeled `break` (`break outerLoop;`) does not.** Found piloting PathKit against a real signal-driven poll loop (`shippingWorkflow` in an ecommerce-fulfillment sample project): a `while` loop's body contained an `if` whose only content was a bare `break`, and before this was fixed, `break` was invisible to the graph builder entirely — the `if`'s "true" branch fell through unchanged and was closed as an ordinary `"retry"` back-edge, indistinguishable from the loop simply continuing, so the branch's real destination (the code after the loop) never appeared in the graph at all, and the rendered Mermaid diagram showed two identical `"retry"` edges from the same node instead of one `"retry"` and one path to the post-loop code. A `GraphBuilder`-internal stack (one frame per loop being processed, popped after) now captures an unlabeled `break`'s open edge and merges it into the enclosing loop's `"exit"` outcome instead. A **labeled** `break` (`break outerLoop;`, breaking a loop other than the nearest enclosing one) is not specifically recognized — it falls through to the same "plain statement, nothing branch-worthy" default handling as before the fix, which is likely still wrong for the same reason, just not verified against a real fixture. `continue` (labeled or not) is also unhandled, for the same reason and with the same likely-still-wrong fall-through behavior — neither is currently known to appear in the shipped `demo/` fixtures or the pilot project's 8 workflows, so neither has been fixed yet; both are open follow-ups, not silently-declared-safe.

- **A `try`/`catch` that isn't recognized as wrapping an activity call is fully transparent.** Its `try` block is assumed to succeed and walked through normally, but its `catch` block's contents — including any branches inside it — are not explored or represented in the graph at all.

- **All termination funnels into a single generic `End` node**, whether the function returned a value normally or an uncaught exception propagated out of it. The graph does not distinguish a successful completion from an unhandled error — both just reach "End".

- **If a single statement contains more than one `Promise.race`/`condition()` call** (a rare pattern), only the first one encountered in source order becomes a decision node; any others in that same statement are not separately represented.

- **Path enumeration caps at `maxPaths` (default 2000), for cyclic and acyclic graphs alike** — a large but ordinary workflow with many independent branches can hit this just as a workflow with a retry loop can (12 independent if/else pairs alone already produce 4096 possible paths). When the cap is hit, the result is marked truncated and includes whichever paths a depth-first, edge-order traversal reached first — there is no attempt to select a "representative" diverse sample of the excess.

- **A retry loop's back-edge is only ever taken once per enumerated path.** This is what makes a cyclic graph's path enumeration terminate at all, and deliberately does not enumerate "0 retries", "1 retry", "2 retries", etc. as separate paths — a single path containing the retry edge represents "a retry happened," not any specific iteration count. Reasoning about how many times a loop can actually run requires inspecting the graph structure directly, not the path list.

- **A path is a flat ordered list of edge labels, with no reference to which decision node each label came from.** Two unrelated decision points that happen to produce the same label text (e.g. two different `if` statements both producing a `"true"` edge) are not distinguishable from the path list alone — only from the graph's nodes/edges.

## Gap 2 — workflow path coverage tracking

Gap 2 reuses Gap 1's graph/path engine to auto-instrument a copy of a workflow file, run it for real through a Temporal `TestWorkflowEnvironment`, and merge recorded execution traces back against Gap 1's declared paths to report coverage. It is complete as of G11 (see `PLAN.md`'s "Gap 2" section for the milestone history). Everything below is specific to this feature — Gap 1's own static analysis is unaffected by any of it.

### Known bug, not yet fixed — a decision nested inside a `try` block never matches its declared path

**Found piloting coverage tracking against a real project's saga-orchestrator workflow** (`orderFulfillmentWorkflow` in `ecommerce-fulfillment-temporal`, which has `if (shipment.status === 'exception') { ... }` as an ordinary statement inside a larger `try { ... } catch (err) { ... }` block, with more code — including the workflow's normal return — after that `if`). Two real, passing tests exercised this workflow end to end, recorded real traces via `recordCoverageTrace`, and `pathkit report` still reported those paths as `missed`, with the underlying trace files logged to `unmatchedTraces` as "does not correspond to any currently-declared path" — even though the code they ran is exactly what the declared path describes.

Root cause: `mergeCoverageTraces` (`coverageReport.ts`) compares a raw runtime trace's push order against `enumeratePathsWithEdgeIndices`'s declared-path edge order (`graph.ts`), and silently assumes these two orderings always agree. They don't, for a decision nested inside a `try` whose own `try`-block has more statements after that nested decision. `tryCatchEdits` (`instrument.ts`) inserts the `try`'s own "success" push at a fixed position — right before the `try` block's closing `}` — regardless of what's textually between the nested decision and that closing brace. So at runtime, a nested `if`'s push fires *before* the enclosing `try`'s "success" push (the `if` runs first, textually and temporally). But `enumeratePathsWithEdgeIndices`'s graph traversal visits the `try` node itself before descending into whatever follows its "success" outcome — which is where the nested `if` sits in the graph model — so the *declared* path lists the edges in the opposite order: try-success, then the nested `if`'s outcome. Concretely, for this project's workflow: runtime trace `[..., shipmentExceptionEdge, trySuccessEdge]` vs. declared path `[..., trySuccessEdge, shipmentExceptionEdge]` — same edges, wrong order, and `mergeCoverageTraces`'s `arraysEqual` treats that as a non-match.

This is a genuine correctness bug, not a documented scope boundary like the rest of this section — but it's not a small, isolated fix either, which is why it's recorded here rather than patched on the spot. Two candidate approaches, each with a real tradeoff not yet weighed by the project owner:

1. **Make trace comparison order-independent** (compare as a multiset/sorted set of edge indices rather than a sequence). Simple to implement, but risks conflating two genuinely different paths that happen to touch the same set of decision points in a different order — plausible for more deeply nested control flow than this bug's example, so it would need real scrutiny before trusting it not to silently merge distinct paths.
2. **Make declared-path edge order match physical/runtime push order** (change `graph.ts`'s path enumeration, or `instrument.ts`'s push-insertion positions, so a `try`'s own resolution edge is always ordered relative to nested decisions the same way `instrument.ts` actually pushes them). More correct in principle, but touches the core graph/path model shared by Gap 1's static analysis too — a change here needs to be checked against every existing fixture, not just Gap 2's own tests, since `enumeratePathsWithEdgeIndices`'s traversal order is also what `pathkit analyze`'s plain-text and Mermaid output present as each path's textual description.

Not attempted in this pass — flagged for a project-owner decision rather than guessed at, per this project's own established norm (see Gap 1's `executeChild()` entry above for the same pattern). In the meantime, any workflow with a decision nested inside a `try` block that has more code after that decision (not just a bare `return` as the try's very last statement) will systematically under-report coverage for every path that goes through that nested decision — the trace is real and correct, but will never match.

### Internal mechanics (mostly invisible unless you're extending PathKit itself)

- **`buildWorkflowGraphWithNodeRefs`'s `Node` references are only valid against the exact `ts-morph` source they were built from.** They must never be reused after that source has been mutated (e.g. by instrumentation inserting text into a copy of the file), and never across two different parses of "the same" file, even if the file's text is identical — `ts-morph` node identity is tied to the specific `Project`/`SourceFile` instance that produced it. Any code that needs a node-to-source mapping for a mutated or freshly-reparsed file must call `buildWorkflowGraphWithNodeRefs` again, fresh, against that exact source.

- **A retry loop's own back-edge closing can overwrite the persisted label of whichever nested decision's continuation happens to fall through to the end of the loop body** — e.g. an `if` with no `else` whose only content is an early `return` has its "false" continuation persisted in `graph.edges` with the label `'retry'`, not `'false'`, if nothing else inside the loop body consumes it first. This is intentional in Gap 1's own graph model (a single combined "retry" edge is exactly the semantics `mermaid.ts`'s rendering and `paths.ts`'s path enumeration want), but it means instrumentation cannot safely find "the edge for this if's false outcome" by searching `graph.edges` for a `'false'`-labeled edge, since it might not exist under that label at all. `buildWorkflowGraphWithNodeRefs` therefore also returns `outcomeEdgeIndex: Map<string, number>`, keyed by a stable `${nodeId}#${originalOutcomeLabel}` tag set at the moment each decision's own outcome edge is created, resolving to that edge's final index in `graph.edges` regardless of what label it ends up persisted with. All of `writeInstrumentedCopy`'s edit-generation functions use this map, never `graph.edges.find(...)` by label, for exactly this reason.

- **Live end-to-end coverage tests need a real Temporal test server and are noticeably slower than PathKit's pure-static tests.** `TestWorkflowEnvironment.createTimeSkipping()` downloads an ~80MB ephemeral test-server binary to `/tmp` on first use (not a persistent OS cache directory), and each distinct instrumented file bundled via `Worker.create({ workflowsPath })` costs real Webpack bundling time (a few hundred milliseconds per unique file, not shared across different files). This is a fact about the Temporal SDK's own testing infrastructure, not something PathKit controls — PathKit's own CI caches the downloaded binary to pay that cost only once per `@temporalio/testing` version.

### What can actually be instrumented (narrower than what Gap 1 can detect)

Rewriting a workflow file's source is strictly harder than recognizing a pattern in it, so the *instrumentable* subset of each construct below is narrower than the *detectable* subset Gap 1's own scope boundaries (above) describe.

- **A function must have a block body (`{ ... }`) to be instrumented at all** — an implicit-return arrow function (`export const x = async () => expr`) has nowhere to put the coverage query's `setHandler` call and fails loudly with a `PathKitError` rather than silently producing an uninstrumented copy. A workflow file that imports from `@temporalio/workflow` using a namespace import (`import * as workflow from '@temporalio/workflow'`) or a bare side-effect import (`import '@temporalio/workflow'`) is also not supported yet — only the named-import form (`import { proxyActivities, ... } from '@temporalio/workflow'`, with or without existing names) can have `defineQuery`/`setHandler` merged into it; both unsupported shapes fail with a clear `PathKitError` at instrumentation time rather than instrumenting incorrectly.

- **A try/catch's "success" push can be skipped if the try block contains its own early `return`/`throw` before its last statement.** The success push is inserted as the literal last statement of the `try` block, which correctly fires for the realistic, common shape (the try body is a short, straight-line sequence ending in the guarded activity call or falling through normally) — but if a nested construct inside the try body (e.g. an `if` with an early `return`) exits before reaching the try block's final statement, that specific execution path never reaches the success push, even though no exception occurred. This under-counts "success" coverage only for try bodies with internal early exits; it never mis-records a success as a failure or vice versa, since the push is always textually positioned after everything that could throw. Gap 1's own graph still correctly models any nested branching inside the try body as its own separate decision node(s), which is still correctly instrumented — only the try/catch's own aggregate success/failure push can be missed in this shape.

- **What can be instrumented for `Promise.race`/`condition()` is narrower than a first read of the plan might suggest, because of how `graph.ts` actually walks the AST — not an arbitrary restriction.** `graph.ts`'s statement dispatch checks `if`/`try`/`while`/`for` *before* ever checking a statement for a `Promise.race`/`condition()` call, so a call embedded in one of those constructs' own test expression (e.g. `if (await condition(fn, timeout)) {...}` or `while (await condition(fn, timeout)) {...}`) never becomes a `Promise.race`/`condition()`-kind decision node at all — it's absorbed into an ordinary `if` decision or a transparent loop, with no special timer/signal semantics. The only statement shapes that can ever produce one of these decision nodes are "plain" statements (an expression statement or a variable declaration) not otherwise claimed by an `if`/`try`/`while`/`for`/`return`/`throw` handler. Within that real scope, the *instrumentable* subset is: a `Promise.race([...])` call must be a bare, value-discarding statement (`await Promise.race([...]);`, with nothing consuming its resolved value — the only shape found in real code, per `temporalio/samples-typescript`); a `condition(fn)` call (no timeout) can appear in any such plain statement, since it has only one possible outcome; a `condition(fn, timeout)` call (with timeout) must be captured into its own variable declaration (`const x = await condition(fn, timeout);`), since only the captured boolean tells the two outcomes apart. Any other usage — the race's result assigned to a variable or returned, or a with-timeout `condition()` call whose result is discarded — fails loudly with a `PathKitError` at instrumentation time rather than guessing or silently skipping it.

- **The generated `__pathkitRace` helper never exposes or preserves the race's own winning value**, only which side won (as a label string) — consistent with the "bare, value-discarding statement" restriction above. If a future version needs to support a `Promise.race` whose resolved value is actually used, the helper and its call sites will need to change to also thread the value through, not just the label.

### Coverage-reporting semantics

- **`sourceHash` will flag a false "stale" warning on any text change to the workflow file, including pure formatting or comment edits, not just changes that actually alter branches or paths.** It is a plain `sha256` hash of the workflow file's full text at the moment a trace was recorded — it has no way to distinguish a cosmetic edit from one that changes control flow, so it is a known, accepted false-positive rate in exchange for the correctness of never silently comparing a trace against control flow that has actually changed underneath it. `pathkit coverage --allow-stale` (or `mergeCoverageTraces`'s `allowStale` option) is the deliberate escape hatch for a known-cosmetic change.

- **A path reported as "covered" for a workflow with a retry loop doesn't tell you whether it succeeded on the first try or only after retrying — both look identical in the report.** For example, a report showing the `"succeeded"` path as covered could mean the underlying test's very first attempt worked, or that it failed twice and succeeded on the third — the report can't tell you which, and doesn't try to. This falls directly out of Gap 1's own graph model: a declared path can only take a retry loop's back-edge once, and doing so forces the next step to be the loop's own "exit" (give up) — so there is no declared path at all representing "retried, then succeeded," only "succeeded" and "retried, then gave up" as separate paths. Coverage matching is honest about this rather than inventing a path that doesn't exist in the graph: it collapses away *how many times* a loop repeated, never *whether* it ultimately succeeded or gave up — so "gave up after retrying" and "succeeded" still reliably show up as two distinct, separately-tracked paths; only the retry count *within* a success is invisible.

- **One `prepareCoverageRun` call instruments and tracks exactly one named function per workflow file.** If a file exports several workflow functions, each one needs its own `prepareCoverageRun`/`recordCoverageTrace` pair (and its own `pathkit coverage --function <name>` report) — there is no single pass that instruments every exported function in a file at once. This matches Gap 1's own per-function graph/path model, and is a deliberate scoping choice, not a current-version-only restriction expected to change automatically.

- **Trace files accumulate indefinitely unless explicitly cleaned up.** Neither `recordCoverageTrace` nor `pathkit coverage` ever deletes a trace file on its own initiative — `.pathkit/coverage/` (or wherever traces are written) will grow across repeated test runs, and a trace recorded against a long-superseded version of the workflow will linger forever, generating `sourceHash`-stale warnings indefinitely. `pathkit coverage --clean` is the explicit, user-invoked cleanup step (deletes every trace file it just read, after successfully building and printing the report) — there is no automatic pruning by age, so a stale trace only goes away when you ask for it to.

- **`pathkit coverage` is report-only — there is no `--min-coverage`-style threshold to fail a CI build on regressed coverage.** The command always exits 0 unless it hits a real error (a missing workflow file, an unreadable traces directory, and similar); a low coverage percentage, or a fully-empty trace directory, is reported but never treated as a failure by the command itself. A CI pipeline that wants to gate on coverage needs to parse `pathkit coverage --json`'s output itself (e.g. checking `percentage` or `untestedPaths.length`) and decide what to do with it.

## Gap 3 — combined multi-file paths + coverage report (`pathkit report`)

Gap 3 (in progress, `H0`–`H6`) adds a `pathkit report <dir> --traces <dir>` command that recursively discovers every workflow across a directory and combines Gap 1's path enumeration with Gap 2's coverage matching into one project-wide view. It reuses both engines' logic unchanged — no new path-matching algorithm, no change to Gap 1's or Gap 2's own scope boundaries above, which still apply per-file/per-function exactly as documented.

- **Directory discovery's "test file" exclusion is a fixed pattern, not configurable.** `discoverWorkflows` skips any file matching `/\.(test|spec)\.ts$/` or living under a `__tests__/` or `test/` directory. A project that colocates its own tests under a different convention (e.g. a `spec/` directory, or a `*.tests.ts` plural suffix) will have those files scanned as candidate workflow files — they'll simply produce zero rows (no exported workflow-shaped functions) rather than being misidentified as a workflow, so this is a false-scan cost, not a correctness bug, but it means a test file that *does* happen to export an async function could theoretically show up as a spurious "workflow" row.
- **`.d.ts` declaration files are always excluded from discovery**, even a hand-written one that happens to declare an exported function — discovery is only ever meant to find real workflow *implementations*, never ambient type declarations, and `parseWorkflowFile`'s own function-collection logic has no way to distinguish "no implementation because this is a declaration file" from a genuine workflow. (Found concretely: running an early version of `discoverWorkflows` against PathKit's own compiled `dist/` directory produced 22 false-positive "workflows" from `.d.ts` ambient declarations before this exclusion was added.)
- **Discovery skips `node_modules`, `test`, `__tests__`, `dist`, `build`, `coverage`, and `.git` directories by a fixed name list** — it does not consult `.gitignore` or any other ignore-file convention, so an unusual project layout with large non-source directories under a different name (nested under the scanned `<dir>`) will still be walked in full. This has not caused a practical performance problem in any real project checked during development, but is a known, unoptimized scan strategy, and the skip list itself is not currently configurable.
- **An unparseable file under `<dir>` is silently downgraded to a warning, never a hard failure of the whole `report` command** — confirmed with the user as the intended behavior (consistent with the project's existing "an unmatched trace is a warning, not a failure" precedent from Gap 2), but it means a directory containing a genuinely broken `.ts` file will never cause `pathkit report` to exit non-zero on that basis alone.
- **`classifyCoverage(0, 0)` (a workflow with zero declared paths) reports 0%, bucket `'none'` — identical to a workflow with real paths that are simply all untested — but this case cannot actually occur for any real workflow.** `graph.ts`'s `GraphBuilder.finalize` always connects every remaining open edge into a distinct `end` node, so even a function with zero branches always yields exactly 1 declared path (confirmed by `test/fixtures/g4/zero-branch.ts`, used throughout Gap 2's own tests). `totalPaths: 0` is handled purely as defensive division-by-zero safety in `classifyCoverage`, not because any real workflow can produce it — it deliberately does not get its own bucket distinct from `'none'`, since there is no real input that would ever surface the distinction.
- **`pathkit report`'s color support (green "covered" / red "missed") only colors individual path lines, never the per-workflow subtotal or project-wide total lines** — a deliberate scope limit matching what was explicitly requested, not an oversight; there is no three-color (full/partial/none) scheme for summary lines. Color is TTY-gated (`isTTY`) and can be disabled via `--no-color` or the `NO_COLOR` env var (any non-empty value); it is never enabled for `analyze` or `coverage`, only `report`. `--out` always writes plain, uncolored text (or plain JSON with `--json`) regardless of the run's own terminal color state, since a file is not a terminal.
- **`pathkit report` has no `--clean` or `--function` flag**, unlike `coverage` — `report` always covers every function `discoverWorkflows` finds under `<dir>` (no single-function targeting), and re-reads the same trace directory `coverage` does without ever deleting from it. A combined report-then-clean workflow isn't supported in this pass.
- **`pathkit report`'s full path listing has no length cap or pagination.** For a project with hundreds of paths across many workflows, the text output can get very long. A `--summary` flag to collapse to workflow-level totals only (subtotal lines without the per-path listing) is a deliberately deferred future addition, not part of this first pass.
- **`pathkit coverage --json`'s output gained one new field, `orderedPaths`, as a side effect of building Gap 3.** `CoverageReport.orderedPaths` lists every declared path in natural declaration order (not grouped by coverage status like `coveredPaths`/`untestedPaths`), each tagged with a `covered` boolean — added because Gap 3's `report` command needs exactly this ordering and it would have been wasteful to re-derive it by re-parsing and re-enumerating the workflow a second time outside `mergeCoverageTraces`. This is purely additive (existing fields are unchanged), but any external tool parsing `pathkit coverage --json`'s exact shape will now see one more field than before this milestone.

## Milestone J — HTML report (`analyze --html` / `report --html`)

- **A workflow's entry in `.pathkit/report-data.json` is never pruned, even after its source file is deleted or renamed.** Neither `analyze --html` nor `report --html` removes an entry for a workflow that no longer exists — the last data recorded for it simply lingers in the HTML report indefinitely. This matches the project's existing precedent for `.pathkit/coverage/` trace files (which also accumulate until `pathkit coverage --clean` is explicitly run) rather than introducing new prune-on-write behavior nobody asked for.
- **The HTML report's per-workflow key is the `(filePath, functionName)` pair, exactly as each command's own CLI invocation recorded it — not a normalized, resolved path.** `report --html` always uses `discoverWorkflows`'s relative-to-`process.cwd()` paths, but `analyze --html` uses whatever `<file>` string the caller typed (absolute or relative). If the same workflow file is referred to by two differently-formatted paths across an `analyze --html` call and a `report --html` call (e.g. an absolute path in one, a relative path from a different `cwd` in the other), the report will show it as two separate entries rather than merging them into one. Always invoking both commands from the same working directory with the same path style avoids this.
