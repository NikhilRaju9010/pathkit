# Known Limitations

PathKit is a static analysis tool. Rather than silently guessing at code it can't reliably interpret, it aims to either detect a pattern correctly or clearly not detect it at all. This file tracks the boundaries of what v1 supports, updated as each milestone is built.

## Scope boundaries (by design, not bugs)

- **Single-file analysis only.** PathKit analyzes one workflow file at a time, passed directly on the CLI. It does not follow imports, does not resolve helper functions defined in other files, and does not do cross-project type resolution. A workflow that splits its logic across multiple files will only show the branches visible in the file actually analyzed.

- **Activity-call detection is a same-file syntactic heuristic, not type resolution.** A call is treated as "an activity call" when it can be traced, within the same file, back to a local `proxyActivities()` / `proxyLocalActivities()` result (e.g. `const acts = proxyActivities<T>(...); acts.foo()`). PathKit does not use the TypeScript type checker to resolve the activity interface across files — only the local call-site pattern is recognized. A call to an activity proxy that was created in a different file, passed in as a parameter, or produced by a wrapper function will not be recognized as an activity call in v1.

- **`switch` statements are not detected as branch points (v1).** Only `if`/`else` is walked for condition branches (M2). A `switch` in a workflow function is simply invisible to the graph — it does not crash the tool and does not appear as a branch, decision node, or path split. This is a deliberate v1 scoping decision, not an oversight: `switch`-based branching can be added in a later version if there's demand.

## Patterns not yet evaluated

Entries below are added as each detection milestone is built, reflecting real gaps discovered during implementation (not written speculatively ahead of time).

- **M3 (try/catch around activity calls):** activity-call recognition, confirmed against real code in `temporalio/samples-typescript` and the SDK's own doc comments, currently covers three same-file shapes: a destructured call (`const { foo } = proxyActivities(...); foo()`), a call through a bound proxy object (`const acts = proxyActivities(...); acts.foo()`), and the SDK's documented per-call override (`foo.executeWithOptions(options, args)` on a destructured activity). It does **not** recognize: a proxy result assigned to a variable and then destructured from that variable in a separate statement (`const acts = proxyActivities(...); const { foo } = acts;`); a proxy result passed into another function or stored in a nested object/array property; or a `try`/`catch` whose activity call is wrapped in a custom helper function rather than called directly. These all fall under the same-file-syntactic-heuristic scope decision above, not new exceptions to it.

- **M4 (`Promise.race` timeouts and `condition()` signal-waits):** a `Promise.race([...])` is only recognized as a timeout branch when the race argument is a literal array expression directly at the call site (`Promise.race([a, b])`); a race over a variable holding an array (`Promise.race(promises)`) is not recognized, since that would require tracing the array's contents rather than reading them off the call. Within a recognized race array, the "timer" side must be a direct or nested call to `sleep(...)` imported from `@temporalio/workflow` in the same file — a custom wrapper function that calls `sleep()` internally (defined elsewhere) is not recognized as a timer, for the same same-file-heuristic reason activity wrapper functions aren't recognized in M3. `condition()` is recognized in both its 1-argument (wait only) and 2+-argument (wait with timeout) forms purely by argument count, with no attempt to verify the timeout argument's type. Signal registration itself (`defineSignal`, `setHandler`) is not treated as a branch point — only the `condition()` call where execution actually waits is; this is intentional, not a gap, since the branching happens at the wait, not at the handler registration.

- **M5 (graph construction):**
  - Only an explicit `while`/`for` loop wrapping a recognized activity call becomes a cycle in the graph (a labeled "retry" back-edge). A loop with no activity call inside it is walked through transparently, once, with no cycle modeled — consistent with if/else being unconditionally a branch but try/catch and loops only being one when they wrap an activity. A `continueAsNew()`-based recursive pattern (a workflow re-invoking itself instead of looping) is **not** recognized as a cycle at all in v1 — only literal `while`/`for` loops are.
  - A `try`/`catch` that isn't recognized as wrapping an activity call (per the M3 heuristic) is treated as fully transparent: its `try` block is assumed to succeed and walked through normally, but its `catch` block's contents — including any branches inside it — are not explored or represented in the graph at all.
  - All termination funnels into a single generic `End` node, whether the function returned a value normally or an uncaught exception propagated out of it (e.g. a `throw` inside a `try`/`catch` that isn't recognized as an activity try/catch). The graph does not distinguish a successful completion from an unhandled error at the type level — both just reach "End".
  - If a single statement contains more than one `Promise.race`/`condition()` call (a rare pattern), only the first one encountered in source order becomes a decision node; any others in that same statement are not separately represented.

- **M6 (path enumeration):**
  - The `maxPaths` cap defaults to 2000 and applies to every graph, cyclic or not — a large but ordinary acyclic workflow with many independent branches can hit it just as a cyclic one can (see the `pathological-explosion` fixture: 12 independent if/else pairs already produce 4096 possible paths). When the cap is hit, `truncated: true` is returned alongside whatever paths were found first — there is no attempt to select a "representative" diverse sample; the included paths are simply whichever ones a depth-first, edge-order traversal reached before stopping.
  - A retry loop's back-edge can be taken at most once per enumerated path (never repeated), which is what makes a cyclic graph terminate at all — this deliberately does not enumerate "0 retries", "1 retry", "2 retries", etc. as separate paths. A workflow whose real retry count matters for testing purposes will need to inspect the graph structure directly (M5's output), not the path list, to reason about iteration count.
  - A path is returned as a flat ordered list of edge *labels* only (e.g. `["", "true", "success"]`), with no reference to which specific decision node each label came from. Two unrelated decision points that happen to share a label (e.g. two different `if` statements both producing a `"true"` edge) are not distinguishable from the path list alone — only from the graph's nodes/edges (M5's output).
